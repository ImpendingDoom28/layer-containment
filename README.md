# Tower Defense Game

A 3D tower defense game built with React, Tailwind CSS, and React Three Fiber.

## Features

- **Tile-based tower placement system** - Click tiles on the grid to place towers; invalid path placement shows red tower preview. While a tower is selected, the hovered tile also shows a range ring (green on buildable tiles, red on blocked ones) so you can judge reach before placing
- **Combat juice** - Gold rewards (`+$N`) float up on each kill, enemies flash white when hit (a transparent per-enemy overlay so same-colored units don't light up together), and a small dual-ring bu rst plays when an enemy dies. Rendered via a pooled camera-facing sprite system and a capped burst list so it stays cheap at peak enemy counts
- **Rocket explosion area of effect** - When a BRL rocket detonates, its blast plays as a short impact: a quick bright fireball (a camera-facing additive sprite) plus a very faint, see-through **shockwave** that sweeps out from the impact point and lands exactly on the projectile's blast radius (`aoeRadius`) before dissipating, so the visible splash area matches the damage area. The shockwave is a single wide, **additive-blended ring at low opacity** (a shared unit `ringGeometry` scaled per explosion, lying flat on the planet via the impact's surface-normal quaternion), so it barely tints the ground — a soft ripple that marks the blast radius without a sharp outline or a filled disc. The whole burst animates in `useFrame` by mutation on the pause-aware simulation clock via the `PROJECTILE_HIT` game event (no per-rocket React state beyond a capped live-explosion list) — it freezes with the world on pause, and the fireball is skipped under `prefers-reduced-motion` (the blast-radius shockwave still plays)
- **Enemy locomotion** - Enemy bodies animate like creatures instead of static assets, driven by ECS rather than the model: `src/constants/enemyLocomotion.ts` maps each enemy type to an animation recipe, `spawnEnemy` resolves it onto the entity's `EnemyLocomotion` trait (bob amplitude in world units, phase seeded by the enemy id so a wave never moves in sync), and the `EnemyLocomotion` renderer wrapper animates the body — model or sphere fallback alike — purely from that trait on the pause-aware simulation clock. The Troop and the R&H drone (medic) walk by swinging their GLB's hip pivots (`Leg_L` / `Leg_R`, matched by name prefix so the medic's `Leg_L001` / `Leg_R001` exports match too) in opposition instead of gliding; the Wraith drone hover-bobs as it travels, and the Splitter's cell colony breathes on a ±3% scale loop. The Splitter also gets a squash-stretch death anticipation: the ECS holds the dead colony back for its `deathPreburstSeconds` window (`requestEnemyDeath.requestedAt`, ~0.28 simulation seconds — still counted as pending by the wave logic) while the renderer squashes it down and wide, then stretches it upward, so the split shrapnel and the death burst land exactly at the pop. All locomotion freezes with the simulation clock and returns to the rest pose under `prefers-reduced-motion`
- **Tower firing feedback** - Towers no longer fire silently. Each shot plays a brief additive muzzle-flash sprite at the barrel tip and a one-shot recoil punch: only the barrel (the turret's barrel node, configured per tower via `muzzle.barrelNode`) kicks back toward its base along the muzzle axis and shrinks, then springs back, so the rest of the turret stays put. Both are driven by the existing `TOWER_FIRE` game event and animate in `useFrame` by mutation on the pause-aware simulation clock (no per-shot React state), and the flash composes with the bloom pass. Both effects are skipped under `prefers-reduced-motion`
- **Tower idle animation** - Between shots, every placed tower carries a small perpetual motion so the board reads as inhabited: the top piece (the aiming turret — or the relay's pulse array, named via `idleNode` in the game config) sweeps a slow scan (±16°) around the yaw it last aimed, a gentle vertical bob, and a subtle breathing of the tower's emissive "energy" accents. All three are slow sines on the pause-aware simulation clock with a per-tower phase offset (tower id hashed by the golden angle, so no two towers move in lockstep), driven by one shared `useFrame` that iterates a small registry the towers fill on model load (each tower costs a few property writes per frame, not its own frame subscription). While a target is live the sim's aim pass owns the turret's yaw and the idle scan holds it; the scan fades in over ~1.2 s after a tower goes idle so a turret that just lost its target never snaps sideways. The per-tower emissive clones (one material instance per tower, the shader program stays shared) make each tower breathe on its own phase without touching the GLTF materials shared by all towers of a type; the animated turret subtrees are flagged out of the frustum-culling staleness snapshot so the idle motion does not re-measure the culling sphere every frame. Everything freezes with the world on pause (and eases with time dilation), and all motion is skipped under `prefers-reduced-motion`
- **Projectile trails** - Every in-flight single-target / AoE projectile leaves a short fading streak behind it so shots read faster: one extra instanced slot per projectile in the existing 500-slot pool (a stretched sphere oriented along the travel direction, length scaled by projectile speed), additive-blended and tinted with the tower color via the per-instance color. The head-to-tail fade is a small shader patch (`src/utils/instancedTrailFadePatch.ts`) that reads the unit-sphere's local Y into a varying and multiplies the alpha and emissive by it, so the tail dissolves into the background without an extra geometry or draw call. Beams and chain bolts already have oriented visuals and get no trail; the whole effect is skipped under `prefers-reduced-motion`
- **ECS-backed visual effects** - The spawn and end-of-path ring bursts are koota ECS entities (an `IsEffect` tag, an `Effect` data trait, and the generic `Position` trait). Callers raise a short-lived `spawnEffectRequest` via `effectActions.requestSpawnEffect`; an apply system turns each request into an effect entity, and `EffectSystem` renders the active effects via a `useQuery` subscription. Each entity is destroyed the moment its animation finishes, so the world — not a store array — is the single source of truth for active effects
- **Denied-action feedback** - Trying to place a tower that can't be placed (unaffordable, or on a blocked tile — occupied by a tower/building, on the path, or water) shakes the camera and the tower shop row and plays a short noise cue; the shop row also shakes when a tower card is tapped while unaffordable. Camera and HUD shake are skipped under `prefers-reduced-motion`
- **Denied placement "X"** - When a placement is rejected on a blocked tile, the scene stamps a bright red "X" **above** the tile for ~0.5 s, teaching *why* the tile is blocked alongside the shake/noise. The X is lifted to clear whatever occupies the tile (a tower, a building, a spawn portal, the base, the path, or water), so it always reads against the field. It is one additive shader plane (the X is two rounded diagonal strokes drawn in the fragment shader from a single `uProgress`, which fades it in, holds it fully visible, then fades it out) mounted only for the effect's duration and raycast-disabled, driven by the pause-aware simulation clock. It subscribes to the same `UI_ACTION_DENIED` event the HUD/camera shake use — the event now carries the tile's flat-field `worldPosition` for `blocked_tile` denials — so it is purely view-side and doesn't touch the simulation. Under `prefers-reduced-motion` it holds a static pose (the X shows, nothing animates) before fading out
- **Tower shop** - The shop is a compact panel at the bottom-left of the screen (mobile: a full-width bottom bar of compact buttons). Each tower is a square button whose face is a small rounded 3D preview box: the tower's real model (the same GLB and base-fit transform the placed tower renders, through a self-contained R3F canvas that shares the `useGLTF` cache, so it renders outside the game scene and is already preloaded with the rest of the models) is shown from a 45° top angle, turned 45° and fitted to fill the box, under a bottom-to-top black→transparent gradient with the price in white at the box's bottom, so the cost stays readable against any model. The tower's text description is not shown in the shop (it remains available in the Almanac's Towers tab); the selected tower is highlighted, and a "Cancel selection" button appears in the panel header
- **Micro camera punch on big events** - Reuses the denied-action camera-shake machinery (the same decaying shake offset in `GameCamera`) at a much smaller amplitude for two "big" moments: a tiny kick toward the blast when an AoE / BRL rocket detonates, and a slightly stronger kick when the base takes damage (enemies reaching the end of a path) — the base-damage punch is also paired with a brief red-tinted screen-edge vignette (`HUDBaseDamageFlash`). The explosion and base-damage are new `PROJECTILE_EXPLOSION` / `BASE_DAMAGE_TAKEN` game events (raised by the projectile hit path and the generic `ApplyDamageSystem` respectively), so the punch is purely view-side and doesn't touch the simulation. Both the camera kick and the red flash are skipped under `prefers-reduced-motion`
- **Six tower types**:
  - Basic Tower: Fast firing, single target damage (targets nearest enemy)
  - Slow Tower: Slows enemies on hit with debuff effects
  - BRL (Ballistic Rocket Launcher): Fires a rocket from one of its four top launcher tubes (the tube that fires rotates with every shot) in a ballistic arc — it climbs, peaks, and nose-dives onto its target — then detonates on impact for area damage over a wide radius, the blast made visible by a quick fireball and a ground ring that expands to the blast radius. It's long-range artillery with a **minimum effective range**: enemies closer than 2.5 tiles are out of reach (the rocket needs room to arc), so it only fires on targets between 2.5 and 5 tiles away. When the tower is selected (or hovered during placement) the no-fire area inside the minimum range is shaded with a filled disc under the outer range ring, so the playable 2.5–5 band is the gap between the two
  - Laser Tower: Piercing beam that hits multiple enemies in a line (targets furthest enemy)
  - Relay Tower: Support tower that buffs **edge-adjacent** combat towers (+damage and +range; multiple relays stack with diminishing returns). Does not attack; placement preview highlights neighbor tiles that already hold a combat tower
  - Chain Lightning: First hit on the primary target, then the bolt travels and strikes up to three more enemies in order (each hop deals 15% less damage than the previous hit, multiplicative)
- **Five enemy types**:
  - Troop: Standard enemy with balanced stats
  - Wraith: Fast-moving enemy with lower health
  - Tankee: Slow but heavily armored enemy that causes more health loss
  - R&H drone (formerly "Medic"): Periodically heals nearby allies (not itself); pulse timing respects game pause; a short ring burst plays when the area heal fires
  - Splitter: On death it bursts into a random 2–4 weaker shrapnel that continue along the path and pay no gold (no `+$0` float). Each child spawns at a small random offset along the path (a bounded progress stagger) so the shrapnel scatter around the death point instead of stacking — a single AOE shot can't clear the whole cluster and the burst reads as a spread, not a clump. ECS-backed like the effects: the death system raises a short-lived `splitRequest` trait (carrying the death location and the parent's `split` config), and the `EnemySplitSystem` consumes it to spawn the children. Children never carry the `split` config, so the swarm is bounded to one generation. Splitters only appear in the in-game levels (Sector 1 & 2 waves), not the main-menu scene
- **Enemy wave system** - 7 waves of increasing difficulty with configurable enemy compositions
- **Per-portal enemy assignment** - In multi-portal levels, an enemy group can be pinned to a specific portal (a `pathIndex` on the wave's enemy group in the level JSON, editable per group in the Level Creator's wave panel). Pinned groups spawn only from that portal; groups without one are split evenly across all portals (the rounding remainder goes to the earlier portals), so each wave can mix pinned and freely-distributed enemies. The in-game next-wave preview above each portal lists exactly the enemy types and counts that will come out of that portal, so what the player sees is what spawns. In single-portal levels the field is a no-op — everything still spawns from the lone portal. Sector 2 ships with per-portal assignments on its two fronts
- **Level creator** - Dedicated `/editor` route with a mode rail, contextual inspector, and unified publish flow for placing buildings, drawing paths, painting non-buildable water bodies (same schema shape as buildings; stored in `waters` in level JSON), configuring waves, and exporting schema-compatible level JSON files
- **Terrain** - Buildable land tiles use a procedural regolith-style surface (shader speckle / micro-patches on the top face only) plus sparse 3D rubble props — six concrete-fragment GLB variants (`public/assets/models/rubble_*.glb`), each scattered with a deterministic per-tile randomizer (variant, offset, rotation, scale, and a small per-instance color tint from `hashGrid2D`, so the same level always decorates identically and repeated props don't read as one cloned texture) and rendered as one instanced mesh per variant (with the old box props as the loading/failed-load fallback); path cells and water stay visually distinct; level editor matches the same treatment on land tiles
- **Animated water** - Water visibly ripples, *its reflections move*, and the surface has **depth**: the ripple is a real geometric swell, not just moving shading. A small `onBeforeCompile` patch on the standard water material modulates the surface with an organic wave field — 4 sines plus slow-drifting FBM noise (still procedural, no texture asset) — sampled in **world-space XZ** (so adjacent tiles/bodies share one continuous wave field instead of each pooling its own phase). The ripple animates the emissive glow (the `scene-water-emissive` cyan) and surface tint, modulates the **roughness** so the bright specular highlights shimmer, and perturbs the **surface normal** along the field's gradient (central differences of the height field, so sines and noise share one exact derivative) so the light reflections slide across the water. For depth, the *vertex shader* displaces the top surface along the tile's radial normal by the same world-space field (a fixed small amplitude, bounded by the tile's recess so the swell never pokes through the shore), so the swell has real parallax against the planet: the water `isWater` tiles sit **recessed below the land plane** (a 0.05 dip) so the land edge casts a rim on the water and the swell moves inside the basin; the tiles use a subdivided top face (8×8 grid, so the wave has vertices to swell — a plain box could only tilt) and the `Water` body meshes swell their box/cylinder top too, sitting slightly below the tile surface so a peeking body reads as a deeper pool under the shore. Only the top face and the side top ring move, so the swelled edge matches the swelled face and the mesh stays watertight. The geometry, the lighting, and the reflections all sample the one shared wave field, so silhouette, shading, and displacement stay in phase. The animated material is applied to the visible water surface: the `isWater` tiles on the planet grid (each tile owns a per-tile material instance) and the `Water` body meshes. A single shared per-frame time uniform drives every tile/body — one `WaterClockProvider` per `<Canvas>` writes it once in `useFrame`, so all water animates with a single write and never re-renders. One GLSL program is shared across the whole scene (`customProgramCacheKey`), so there is no per-tile program churn; body materials are additionally cached per color and size (`getWaterMaterial`) while per-tile materials are created fresh and disposed with their tile. The clock is mounted in the game (main menu and play share its canvas), level-editor, and testing-level canvases
- **Enemy upgrade system** - After each wave (except before wave 1), pick one of three random upgrades; choices stack for the rest of the level and apply to all spawns. Full-screen blur modal blocks other UI until you choose. The same upgrade can be taken up to three times with stronger effects each tier; at three tiers it is maxed and removed from the pool. Each tier is an **absolute** effect defined in `public/configs/game.json` (`enemyUpgrades.*.tiers`): picking tier II fully replaces the tier I value instead of stacking on top of it, so balancing is a matter of editing the tier numbers (e.g. Armored I is +50% HP, Armored II is exactly +75% HP, not +50%+75%). Upgrades: Armored (+health: +50% / +75% / +100%), Swift (+speed: +35% / +50% / +70%), Unstoppable (slow resistance: 25% / 65% / immune — only offered as a choice while the player has at least one Slow Tower placed, since it only counters that tower), Regenerating (HP regen: 5 / 10 / 15 HP/s), Reinforcements (each wave spawns more enemies — +20% at tier 1, +40% at tier 2, +65% at tier 3 — applied to every enemy group's count, rounded up, so the relative mix is preserved), and Missing Out (enemies dodge any incoming tower damage with a 5% / 10% / 15% chance per hit). Every pick has a gold reward and picks still multiply each other — Missing Out pays the most (+10% per pick, ≈ +33% over three picks); the other upgrades' per-pick gold bonus was halved, so they grant a smaller gold bonus on top of their stat effect (e.g. Armored I is now +5% gold, Armored I + II ≈ +16% gold). The upgrade panel shows every previously chosen upgrade in a "Selected upgrades" strip (name, tier, and its stacked gold bonus, e.g. `Armored II +16% gold`) so you can see what you already have. The game stats card also carries a "Selected upgrades" button that lists the picked upgrades as one entry each (name, tier, and its stacked gold bonus) and opens a modal with the full list; it appears as soon as the first upgrade is picked and stays visible for the rest of the level so you can re-check it mid-game without pausing (opening the modal blocks camera control, like the menus)
- **Upgrade visuals on enemies** - Each pick is shown as a physical effect on the enemy (1 pick = 1, 3 picks = 3), showing what the upgrade does: small 3D shield plates in front of the body for Armored, a shallow purple glow shell hugging the body for Unstoppable, a subtle green ground ring (thin, wider than the body, growing per tier) emitting a stream of green particles that rise from the ring's edge for Regenerating, white speed straps trailing behind the enemy along its travel direction for Swift, and a pale-blue "phantom" shell around the body that pulses in and out for Missing Out — it also floats a "MISS" text over the enemy when it successfully dodges a hit. Reinforcements tints the spawn portal more orange per tier and adds one pulsing ring per pick, so the upgrade is visible at the portal itself
- **Economy system** - Earn money by killing enemies, spend it on towers
- **Tower management** - Click on placed towers to view info and sell them (50% refund)
- **Audio system** - Sound effects with adjustable volume controls (master, SFX, music, ambient); gameplay SFX use Web Audio spatialization from world positions and the camera, while UI clicks and screen feedback (pause, win, lose, resume) stay non-spatial
- **Rebindable controls** - A "Controls" section in Settings (main menu and in-game menu) lists the player-facing keyboard controls in a table; click a row and press a key (or chord) to rebind it, press Escape to cancel, and a Reset button restores defaults. Bindings use physical key codes so they behave the same across keyboard layouts, and persist to localStorage
- **Control schemes** - Settings / Controls offers two switchable presets: **Keyboard** (the classic WASD/Q+E) and **Touch (mobile)** (a numpad-style number-row layout for screens without WASD). Switching a scheme resets the whole binding set to that preset (and persists it); individual keys can still be rebound afterwards. On a mobile viewport with the Touch scheme selected, two on-screen controls appear in a two-thumb layout: a **D-pad** (bottom-right, mirroring the numpad layout) that drives the camera — hold a button to move, release to stop — and a **rotation joystick** (bottom-left, the touch analog of mouse-drag) that rotates the camera as you drag it
- **First-run controls intro** - The first time a level is started, a "How to play" modal explains the mouse and keyboard controls (showing the player's current bindings) and notes that controls can be reviewed later in Settings / Controls. It appears only once — the flag is remembered in localStorage, so returning players start straight into gameplay
- **Game over / victory animation** - The game-over and victory modal fades in and slides up from the bottom (with a subtle zoom, matching the Empower Next Wave panel) when a run ends, and slides back out the same way when the player restarts or returns to the main menu. Final stats stay frozen during the exit so the numbers don't change mid-animation, and interaction is blocked while it animates away
- **Next Level button** - On a victory, the result screen offers a **Next Level** button (the primary action, with **Play Again** stepping back to an outline button) that starts the next level in the `PLAYABLE_LEVEL_IDS` sequence with that level's own starting health, reusing the same start-with-level flow as the menu's level picker, and clearing the picked enemy upgrades and the wave-readiness state so the new level starts clean. It is hidden on a defeat and on the final level (no wrap-around)
- **End-of-run stats** - The victory/defeat screen reports a fourth stat, **Total Earned** (kill rewards only), and a per-tower-type table (built on the shared `UITable` component) with **Damage** dealt (effective, clamped at 0), money **Spent** on purchases, and **Kills** (with a per-enemy-type breakdown in the kills cell). Tower and enemy rows are derived from the game config, so new types appear automatically. Only tower types that did something appear. It is ECS-backed: actions raise short-lived receipt entities (`damageDealtRequest` / `moneyEarnedRequest` / `moneySpentRequest`), and a `StatsSystem` folds them into a single per-run `IsStats` entity (composed of small atomic traits) before destroying the receipts. When a run ends, the end-state transition tags the stats entity with `RunEnded`; the session pipeline folds same-frame receipts and clears the tag before the result screen reads its snapshot. The run stats entity is spawned on run start and destroyed when returning to the main menu, so the main menu collects nothing
- **Main menu** - Editorial-style start screen with left-rail navigation, large typography, slide-in transitions, and optional GitHub/source icon (`VITE_REPOSITORY_URL` in `.env`). Behind the ambient enemies, the menu renders the same planet tiles as the in-game scene: the `level_main` board with the regolith-shaded land tiles, the path, and the instanced rock props — purely visual (no tower placement, no hover highlights)
- **Logo** - SVG mark for the app (`public/logo.svg` full tile, `public/logo-mark.svg` transparent mark). Containment reticle with four hourglass-shaped layer plates that pinch toward an orange core, matching the `--primary-hex` accent. Set as the favicon in `index.html`
- **Menu parallax** - In the main menu and in-game pause menu, the tilted panels follow the cursor with a subtle eased rotation and shift, and their canvas-side edge lifts toward the viewer as the pointer nears (receding when it moves away). Off during gameplay, on mobile (the tilt is disabled below the `md` breakpoint), and under `prefers-reduced-motion`
- **Time-dilation pause** - Pausing eases the world to stillness over ~200ms (enemy movement, travelling projectiles, and decorative effects slow down instead of freezing instantly) and resumes with a matching ramp; `prefers-reduced-motion` snaps instead of easing. Game logic (slow expiry, regen, heal timing, tower fire) still freezes hard the instant the pause begins, and projectile hits / enemy end-of-path damage are deferred until the world resumes
- **Level picker** - Play opens a sector list with SVG map previews, each level's `label` as the title, a one-line `description`, the wave count, and one-tap start for each playable level (menu-only `level_main` is not listed). Three playable sectors ship in the default build: **Sector 1** (single front), **Sector 2: The Convergence** (two fronts), and **Sector 3: The Coil** (a spiraling single channel). See [Levels](#levels)
- **3D asset showcase (`/testing-level`)** - A non-playable route that displays the whole 3D model roster at once: every enemy type, every tower type and its projectile, buildings (box + cylinder), water bodies, the path with its spawn portal and end building — laid out one tile apart in rows on a 20×20 board. The level loads through the same `LevelSystem` / level-config pipeline as playable levels (`level_testing.json`), but the scene intentionally skips `EntitiesSystem` so no movement, tower-fire, projectile, death or split systems run: enemies and towers spawn and then simply render in place as a frozen snapshot. The level's static projectiles (not fired by any tower) are drawn by a dedicated `StaticProjectiles` component that mirrors the in-game instanced-pool shapes (sphere for single/AoE, oriented cylinder for the laser beam and chain bolt, a rocket with fins for the BRL's ballistic shot, plus an AoE blast-radius ring). **Every enemy upgrade is showcased at all its tiers** (armored, swift, slow-resistance, regenerating, missing-out) on `basic` enemies in a zone spaced from the base assets, and the **reinforcements** upgrade is shown as a row of spawn portals (tiers 1–3, warming green→orange with one pulsing ring per pick) — the in-game `Path` portal always renders at tier 0, so the scene renders these showcase portals directly. A `PerspectiveCamera` + drei `OrbitControls` frame the board so it can be orbited and zoomed to inspect any asset. The route is always reachable by navigating to `/testing-level`; a **Testing Level** button also appears in the main menu (directly below Level Creator) but **only in dev builds** — it is gated behind `import.meta.env.DEV`, so it is stripped from production while the URL remains available.
- **Mobile support (adaptive HUD/GUI)** - The HUD and GUI adapt to narrow screens (below the 768px `md` breakpoint): the tower shop becomes a horizontally scrollable bottom bar of compact square buttons, each a 3D preview box with a gradient and price (scrollbar hidden), the money/health/wave HUD collapses into a compact top strip with the card background (the "Start next wave" button and the game menu button live inside the strip — desktop uses ESC), the main menu panel spans the full width, side panels (menu, almanac, level picker, game menu) are full-width with reduced padding, and the game-over stats wrap. `useIsMobile` (`src/core/hooks/useIsMobile.ts`) mirrors the Tailwind `md` breakpoint for layout switching, and the page tracks the mobile browser chrome via `100dvh` sizing
- **Almanac** - Reference panel with a tab selector between three sections: **Enemies** (bestiary that tracks discovered enemy types with stats and descriptions, persisting to localStorage), **Towers** (every tower type with its cost, damage, range, fire rate, targeting, and type-specific traits like slow/AoE/pierce/relay/chain), and **Upgrades** (every enemy upgrade with its effect and gold bonus). Discovery state also drives the in-game **next-wave preview**: enemies you haven't met yet appear as a masked "???" entry (neutral color, italic) instead of revealing their name, matching how the almanac shows undiscovered enemies. A boss wave additionally shows the boss as a distinct red row with its upgrade-scaled HP
- **Wave controls** - Start waves early or wait for automatic wave progression
- **3D graphics** - Built with React Three Fiber for immersive gameplay
- **Bloom post-processing** - A single `Bloom` pass from `@react-three/postprocessing` (in an `EffectComposer`, `src/components/scenes/shared/PostFX.tsx`) adds a real glow halo to every emissive element: the portal pulse, water, tower preview, hit-flash, range rings, and floating text. A modest luminance threshold (~0.7 in linear space) keeps only hot emissives glowing — the rest of the scene renders untouched — and the bloom is computed at half resolution to stay cheap. It is on by default and toggleable in **Settings → Quality** ("Bloom (glow)"); the setting persists to localStorage, and with it off the composer unmounts so R3F falls back to the plain scene render at zero cost. It is also auto-disabled on software (CPU) WebGL renderers (SwiftShader / llvmpipe — headless CI, older hardware), where a fullscreen pass would starve the main thread (`isSoftwareRenderer` probe). The same component is mounted in the game, testing-level, and level-editor canvases
- **Shader skybox** - The sky dome (`src/components/scenes/shared/Skybox.tsx`) is a single gradient-shader sphere — slightly lighter at the horizon with a faint cyan/green tint, darker overhead — and all stars live in one `THREE.Points` draw call instead of ~450 individual star meshes. The star shader animates per-star twinkle (phase-offset opacity oscillation) and a very slow parallax drift (each star rotates around the sky at its own rate), driven by a single `uTime` uniform; the whole subtree stays matrix-frozen since only uniforms animate. Star point sizes are scaled from the camera fov and pixel ratio so they keep a constant world size at any resolution
- **Real-time shadows** - The scene's key light casts shadows (`src/components/scenes/shared/Light.tsx`): towers, enemies (each a 3D model), rock props, the buildings at the path ends, and live tower projectiles (the instanced projectile and chain-bolt pools; beams and glow trails are excluded) all `castShadow`, while the planet ground, tiles, water, and the path strips themselves `receiveShadow`, so the whole board is lit with a single 2048px shadow map from an ortho camera sized to the level grid (PCF soft shadows). It is on by default and toggleable in **Settings → Quality** ("Shadows"); the setting persists to localStorage. Shadows are also auto-disabled on software (CPU) WebGL renderers via the same `isSoftwareRenderer` probe — the shadow-map pass is far too slow under SwiftShader, the same reason bloom is skipped there. Toggling the setting flips `gl.shadowMap.enabled` at runtime (with a shadow-map re-render), so the change applies immediately without remounting the scene
- **Hemisphere fill + rim lighting** - The scene's flat ambient fill is replaced by a hemisphere light (`src/components/scenes/shared/Light.tsx`): a cyan-tinted sky term (matching the skybox horizon tint) shades up-facing surfaces while a neutral gray ground term bounces up from below, so the fill has direction instead of flattening every model. A second, dim cool-blue directional on the far side of the board from the default camera acts as a rim/backlight: it casts no shadow and just grazes the back and top edges of towers and enemies, silhouetting them against the dark sky for a cheap depth cue
- **Quality settings section** - The graphics-quality options (Bloom and Shadows) live in their own **Settings → Quality** section (`HUDSettingsQualitySection.tsx`), separate from General (language + pause-when-tab-hidden), Audio, and Controls. Both options default to on and persist to the same `containment-layer-settings-v1` localStorage store as the rest of the settings
- **3D model bodies for every enemy type** - All five enemies render as 3D models instead of colored spheres: each model from the Tower Defense entities collection is extracted to its own standalone GLB under `public/assets/models/` (troop, wraith, medic, splitter, tankee — ~770 KB total), recentered, rescaled to the body's diameter, and yawed so its nose points along the enemy's direction of travel. They render through the generic `ModelLoader` (below): every GLB is preloaded at app boot (`useGLTF.preload` in `src/constants/models.ts`) so the first wave of any type never suspends the scene; `ModelLoader` isolates the object in its own `Suspense` + error boundary (fallback = the old colored sphere) so a slow or a *failed* load (404/parse error) only degrades that enemy to the sphere instead of unmounting the whole scene. All enemies of a type share one cached parse of the model (the node is cloned per enemy, geometry/materials shared). The models' baked-in accent colors match each enemy type's color in the game config
- **3D model bodies for every tower type** - All six towers render as 3D models instead of the primitive cylinder/cone/coil: each model from the Tower Defense entities collection is extracted to its own standalone GLB under `public/assets/models/` (tower_basic, tower_slow, tower_aoe, tower_laser, tower_relay, tower_chain — ~890 KB total). The model's **base** (the parts touching the ground — the chassis, since turrets and barrels are elevated) is fitted to the tile footprint and recentered on the tile, then the whole model is grounded so the base sits on the ground; this keeps the bases of all six towers the same size and centered even when a turret overhangs the base (long barrels on the basic/laser towers, a tall sphere on the slow tower). They render through the same generic `ModelLoader`. Unlike the enemy models (preloaded at app boot), a tower's model URL and node live in the game config (`public/configs/game.json`, `towerTypes.<type>.model`), so its GLB is preloaded once the config has loaded (see `GamePage`); the loading screen waits on both so the first visible frame is fully populated. Unlike enemies a tower's base is not yawed (it has no direction of travel); instead the turret is a separate rotating node that swings to aim at the target (see **Turret rotation and aim-gated firing** below). The translucent, color-coded **placement preview is the model itself** (a `TowerModel` "preview" variant), not a placeholder: the same GLB is rendered with a translucent (50%) ghost material, and an invalid drop tints that ghost the destructive red — so what the player drags around is exactly what gets placed. Only the ghost's materials are cloned (shared per tower type/variant, reused as the cursor crosses tiles); the geometry stays shared with the placed tower. The old primitive body survives solely as the model's load-failure fallback, so a missing GLB still degrades a tower to the primitive body rather than unmounting the scene. All towers of a type share one cached parse of the model. The models' baked-in accent colors match each tower type's color in the game config
- **3D model body for the player base** - The base at the end of every path renders as the `Player_Base` 3D model instead of the plain primitive house: a walled fortress with corner bastions, a central keep, and an emissive health core, shipped as its own standalone GLB under `public/assets/models/` (`player_base.glb`, extracted from the Tower Defense entities collection, root node `Player_Base_ROOT`). The model's rest transform is grounded at `y = 0` and centered on x/z (~1.8 × 1.75 × 1.6 units at rest), and it is scaled to `BASE_MODEL_SCALE` (0.75×) so it reads as a structure on the tile rather than a landmark. It renders through the same generic `ModelLoader` — one shared cached parse, one clone per base, geometry and materials shared, shadow flags enabled in the clone. Its **entrance** (the gate and front-buttress side, the model's local +Z) is yawed to face the path's approach (last → previous waypoint): in the game scene that yaw is baked into the surface quaternion, and in the flat editor it is passed as `pathYaw` — so the gate looks down the path enemies enter along. Because the base is static (its URL is known at module load, unlike the towers' URLs, which live in the game config), the base GLB is preloaded at boot alongside the enemy models (`src/constants/models.ts`) — which also covers the level editor, which has no loading gate — and it is part of the "Loading models…" wait, so the first visible frame is a fully-populated scene. The old primitive house survives solely as the model's load-failure fallback, so a missing GLB degrades a path end to the plain house rather than an empty one. Its subtree is frozen on load (`freezeSubtree`), so its ~50 nodes skip per-frame matrix work
- **Turret rotation and aim-gated firing** - Each tower's barrel turns to track the enemy it is shooting instead of firing from a static orientation: the model's turret node (a per-type name in the game config, `Azimuth`/`Field_Array`/…; the relay is excluded as it never fires) is rotated by a per-frame eased swing (`1 - exp(-8 · dt)`, the same rate and exponential ease the enemies use to turn their facing), so a turn decelerates as it converges. A tower only fires once its barrel is within 15° (`TOWER_AIM_TOLERANCE`) of the target direction (shortest arc), so a projectile never arcs sideways off a tower that is still swinging around; while a target is in range but the turret is still turning, the barrel keeps tracking it even through its cooldown. With no enemy in range the turret holds its last aim (it does not swing back to rest). The shot, the laser beam start, and the fire sound all leave the **barrel tip** rather than the tower centre: the muzzle point (a per-turret local constant in the game config, `towerTypes.<type>.muzzle`) is transformed by the live node's `localToWorld`, which applies the model fit scale, base recentering, planet curvature, and the turret's current aim in one step. When the model is still loading (or falls back to the primitive) there is no turret node, so firing is still aim-gated by the logical yaw and the shot falls back to the old centre emitter
- **`ModelLoader` (generic GLB loader)** - Loads a GLB by URL through the shared `useGLTF` cache, extracts a named node, optionally applies a per-model `prepare` transform (rescale / recenter / reorient / ground — e.g. `prepareModel` for enemies, `prepareTowerModel` for towers), and renders it as a `<primitive>` in its own `Suspense` boundary. Without `prepare` the node is cloned so several instances never share a scene-graph parent. Both enemies and towers render through it; adding a new model entity is: point a `ModelLoader` at its URL + node, pass its `prepare`, and (for enemies) wrap it in `HitFlash` — no loader/flash/culling support code per model
- **Model-derived hit marker** - The damage hit-flash is no longer a fixed sphere: it is a copy of the enemy's own body re-pointed at a per-enemy transparent flash material, so its shape always matches the body (the Wraith gets a Wraith-shaped envelope, a box model would get a box) with no per-model support code. A generic `HitFlash` wrapper (composition-style HOC) wraps the body and provides the marker: it renders the body once, keeps a hidden deep-clone of the body's rendered subtree re-pointed at the flash material and scaled 1.12× about the body center, and hands the marker to `Enemy` via a ref. `Enemy` animates the shared flash material's opacity on a hit and toggles the marker's visibility. The clone is rebuilt only when the body's rendered node changes (a Suspense body falling back to its placeholder, then resolving to its model), so the marker always tracks the current body; the clone references the shared body geometry, so the `primitive` is mounted with `dispose={null}` to keep R3F from freeing the shared buffers
- **Frustum culling for entities** - Enemy and tower groups are culled against the camera view each frame: when a group's bounding sphere leaves the view (with a 2-unit hysteresis margin so fast units don't pop at the edge) its `visible` is toggled off and three.js skips the whole subtree in the render pass. Toggling `visible` doesn't remount anything and doesn't affect raycasting (three tests `layers`, not `visible`), so hover and click keep working. The bounding sphere is measured once per group and re-measured when a descendant's transform changes (a heal ring scaling up, an upgrade ring appearing) — detected cheaply by comparing a per-group transform snapshot each frame, so steady-state frames skip the bounding-box walk. The per-frame view frustum is built once and shared across all culled objects, and only rebuilt when the camera actually moves, rotates, or changes its FOV. The preview tower is exempt (it follows the cursor and is always in view). Separately, while the camera is being dragged with the mouse, R3F's full-scene raycast (normally fired on every `pointermove`) is suppressed in the capture phase, so dragging the camera stays smooth. That suppression has two follow-up costs the camera handles itself: R3F's click-distance check only gates `onPointerMissed` — a `click` after a drag would still dispatch `onClick` to the hit object and place a tower — so the camera swallows the click in the capture phase when the pointer travelled beyond R3F's own 2px threshold; and with no `pointermove` R3F never un-hovers the tile under the cursor, so on release the camera re-dispatches a `pointermove` on the canvas at the final position to reconcile the hover highlight
- **JSON-based configuration** - Game settings, tower stats, and level data stored in JSON files
- **Explicit loading flow** - Full-screen black loading HUD while the game is ready: it stays up until the game and level configs load, the shaders compile, **and every 3D model GLB is loaded** (the "Loading models…" step), so the first visible frame is a fully-populated scene instead of an empty board that fills in as models stream in. Model readiness is tracked in `src/constants/models.ts` (`getAreModelsLoaded`), which settles on the same `useGLTF` cache the scene uses — a failed download degrades that one model to its fallback rather than hanging the overlay, and a 15s cap guarantees it always resolves. The loading text in the bottom-right corner with an indeterminate loading bar (the animated SYSTEMS ONLINE badge line) below it slides in from the left on mount and slides out to the right before unmounting (via a shared `useLoadingTransition` hook that keeps the overlay mounted until the exit finishes); `isGameConfigLoaded` and `isLevelConfigLoaded` are exposed from core hooks for UI coordination
- **Simulation vs React frame order** - Wave spawning, tower combat, and instanced projectiles read `useGameStore.getState()` inside R3F `useFrame` so gameplay matches Zustand immediately after tab visibility changes (before the next React commit refreshes hook closures)
- **Desktop app (Electron)** - The game can be packaged as a native desktop application (Windows `.exe`/NSIS installer, macOS `.dmg`/`.app`, Linux AppImage/deb) and distributed outside a browser (e.g. through Steam). The packaged app serves the built `dist/` from a local loopback HTTP server (`http://127.0.0.1`, random port) instead of `file://`, so Web Workers, config fetches, and WebGL behave exactly like the web build. The renderer stays fully sandboxed (contextIsolation on, no Node integration, no `webSecurity` relaxation); links open in the OS browser
- **PWA (installable web app)** - The game is a progressive web app: `public/manifest.webmanifest` declares the app identity (name, theme color, standalone display) and 192/512px icons in both `any` and `maskable` purposes, and `index.html` links the manifest plus an `apple-touch-icon` and `theme-color` meta. A service worker (`public/sw.js`) precaches the app shell (HTML, manifest, icons) at install, serves navigations network-first with an offline fallback to the cached shell, and serves other same-origin assets cache-first with a background refresh — so the game loads offline after the first online visit. Registration (`src/core/pwa/registerServiceWorker.ts`) runs only in production builds on secure origins (https or localhost), so the dev server and the packaged desktop app are unaffected. Browsers can offer "Install app"; the installed app opens in a standalone window. `public/_headers` sets the manifest's `Content-Type` to `application/manifest+json` for the Netlify deployment (some browsers, e.g. Firefox, need the right MIME type to install)
- **Playwright smoke coverage** - Canvas-aware E2E tests cover menu-to-game flow, first-tower placement, first-wave start, and editor route loading; a separate PWA suite (`npm run test:e2e:pwa`, run against `vite preview` because service workers need a production build) verifies the manifest, icon delivery, and service worker registration
- **Localization (i18next)** - All in-game UI text is rendered through locale keys (no hardcoded strings). A language selector in Settings → General switches the whole app live; English is the default and Russian is the first alternate language. The choice persists to localStorage (settings store) and is applied before the first render on load. Locales live in `src/core/i18n/locales/` — `en` is the reference shape (`as const`) that drives TypeScript-checked `t()` keys, and new languages are validated against it by the locale parity tests (missing or misspelled keys fail those tests). Plurals follow i18next suffix rules (`_other`, and `_one/_few/_many` for Russian). React components use `useTranslation`; R3F canvas components use the context-free `useTranslationInCanvas` hook, and non-React code (e.g. upgrade summaries) uses the shared `i18n` singleton from `src/core/i18n/i18n.ts`

Notes:

- The packaged app serves the built `dist/` from a local loopback HTTP server (`http://127.0.0.1`, random port) rather than `file://`. The server is loopback-only, nothing outside the machine can reach it, and no `webSecurity` relaxation is needed.

- F12 toggles the DevTools in the desktop app.

Uncaught renderer errors and renderer-process crashes (usually a GPU failure) also pop up a dialog with the error and the log path. If the app ever fails to start, that log is where the cause lives.
- The desktop app icon is `public/logo.svg` (the same SVG used as the web favicon) — electron-builder converts it into the per-platform app icons at build time: macOS `.icns` and Windows `.ico` are rasterized from the SVG, and on Linux it is placed in the freedesktop `scalable/` hierarchy. No separate icon asset to maintain.
- CI (`.github/workflows/desktop.yml`) builds installers for Windows, macOS, and Linux on every PR and push to `master`, and runs `smoke:desktop` against the packaged app, so a broken desktop build fails CI before merge.
- Distributing through Steam: publish the per-platform installer/artifact builds (NSIS exe, dmg, AppImage) as a Steam app via the Steamworks SDK. No signing/notarization is configured yet — add your code-signing certificates to CI before publishing to the Mac App Store or Steam's notarized macOS builds.

### Commit Conventions

Commits follow [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): subject`, e.g. `feat(towers): add slow tower` or `fix(levels): stop wave counter drifting`.

- **Type**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- **Scope** (optional): the affected area, kebab-case — `levels`, `towers`, `hud`, `ecs`, `stats`, `main-menu`, …
- **Subject**: imperative mood, no trailing period, ~72 chars (the hook enforces a 100-char header limit).

Enforcement is two-tiered:

1. **Local** — a [`husky`](https://typicode.github.io/husky/) `commit-msg` hook runs [commitlint](https://commitlint.js.org/) (`npm run lint:commit`) on every commit, so a non-conforming message is rejected before it lands. The rules live in [`commitlint.config.mjs`](commitlint.config.mjs).
2. **CI** — a [GitHub Actions](.github/workflows/ci.yml) job re-checks every PR's commit messages with commitlint as a backstop, since local hooks can be bypassed.

To lint a single commit by hand: `npx commitlint --last` (checks the most recent commit), or pipe a message: `echo "feat: x" | npx commitlint`.

### Branch Naming

All branches must start with `feature/`, `bugfix/`, `ci/`, `refactor/` or
`chore/` — e.g. `feature/slow-tower`. Note the prefix is `feature/`, not
`feat/`. The mainline `master` is the only exception.

Enforced locally by the [`husky`](https://typicode.github.io/husky/)
`pre-push` hook: a push containing any other branch name is rejected with a
list of the offending branches. Ref deletions, tags, and pushes to `master`
are not affected.

### Pre-push Verification (husky)

The `pre-push` hook first validates the branch names being pushed (see
[Branch Naming](#branch-naming)) and then runs `npm run verify` (build +
unit + e2e) before a push, but only when the push could affect the app. It diffs the refs you push
against their previous remote state (for a new branch, against the merge base
with `master`) and skips verify when every changed file is non-code: all
`*.md` files, `docs/`, `package-lock.json` (alone), and other generated/log
files. Any change to source or app config (`.ts`, `.tsx`, `.js`, `.css`,
`.html`, …) runs the full verify. Ref deletions change no app code, so they
skip too. When the hook cannot determine the changed files, it verifies.

```bash
# docs-only push: verify is skipped
git commit -am "docs: update README" && git push   # → skip message
```

## How to Play

1. **Start the game**: Click "Play" on the main menu to enter the game
2. **View the almanac**: Click "Almanac" to see the reference panel — the Enemies tab shows discovered enemies (undiscovered show as silhouettes), and the Towers and Upgrades tabs list every tower and upgrade with their stats
3. **Select a tower**: Click on a tower in the shop (bottom-left panel; each button shows the tower's 3D model with its price) to select it
4. **Place towers**: Click on a tile in the grid to place the selected tower (cannot place on paths or occupied tiles)
5. **Manage towers**: Click on a placed tower to view its stats and sell it if needed
6. **Start the first wave**: Click "Start next wave" to begin the first wave (gives you time to place towers first)
7. **Defend**: Towers automatically target and shoot at enemies based on their targeting mode
8. **Continue waves**: After each wave is cleared, click "Start next wave" when you're ready to begin the next one
9. **Survive**: Defend against 7 waves of enemies without losing all your health
10. **Win**: Complete all waves to win the game

## Controls

- **Mouse**:
  - Click tiles to place selected towers
  - Click placed towers to select/view info
  - Drag to rotate camera
- **WASD / Q+E** (and arrow keys): Move the camera
- **ESC**: Deselect tower or open game menu
- **Space**: Pause/Resume game

- **Control schemes**: **Settings → Controls** has a scheme switcher — **Keyboard** (WASD/Q+E) and **Touch (mobile)** (numpad-style number row: 8/2 = forward/backward, 4/6 = left/right, 9/3 = up/down). On touch screens with the Touch scheme selected, two in-game controls appear in a two-thumb layout: a **D-pad** (bottom-right) that drives the same camera moves — hold to move, release to stop — and a **rotation joystick** (bottom-left, the touch analog of mouse-drag) that rotates the camera as you drag. ## Game Mechanics

- **Money**: Start with $10,000, earn more by killing enemies (rewards vary by enemy type)
- **Health**: Start with 20 health, lose health when enemies reach the end (amount varies by enemy type)
- **Waves**: 7 waves with increasing difficulty, each containing multiple enemy types
  - Every wave is started manually: the "Start next wave" button appears before the first wave and after each wave is fully cleared, giving you time to build and adjust before the next wave
- **Tower Types**: Each tower has unique stats:
  - **Basic Tower**: $50, 20 damage, 3.5 range, 1s fire rate
  - **Slow Tower**: $80, 10 damage, 3 range, 0.8s fire rate, slows enemies by 60% for 2s
  - **BRL (Ballistic Rocket Launcher)**: $125, 50 damage, 5 range (2.5–5, minimum effective range), 4s fire rate, 1.5 radius area damage
  - **Laser Tower**: $200, 15 damage, 4 range, 2s fire rate, pierces up to 5 enemies
- **Tower Selling**: Sell towers for 50% of their purchase price
- **Targeting**: Towers pick a target each shot. Each attacking tower has a targeting strategy — **Nearest** (closest enemy in range), **Furthest** (farthest in range), **Lowest HP** (weakest enemy in range), **Highest HP** (toughest enemy in range), or **Focused** (keeps firing its last target as long as that enemy stays in range and in line of sight, falling back to the nearest candidate otherwise). The default per tower comes from the game config; you can change any placed tower's strategy at any time from its info panel (select the tower, then use the Targeting carousel selector, which cycles the options with left/right arrows)
- **Projectile Types**: Single-target, area-of-effect, and piercing beam projectiles
- **Audio**: Adjustable volume controls for master, SFX, music, and ambient sounds
- **Almanac**:
  - Accessed from the main menu, with a tab selector for the three sections
  - **Enemies** tab: undiscovered enemies appear as silhouettes with "???" names, revealed when you encounter them in battle; discovery progress persists across browser sessions via localStorage
  - **Towers** tab: lists every tower with cost, damage, range, fire rate, targeting, and type-specific traits (slow, area, pierce, neighbor buff, chain)
  - **Upgrades** tab: lists every enemy upgrade with its effect and gold bonus
- **Enemy Upgrades** (Risk/Reward System):
  - Between waves (starting from wave 4), you can optionally "empower" the next wave
  - Select upgrades to make enemies stronger in exchange for bonus gold rewards
  - Upgrades unlock progressively:
    - Waves 4-6: Tier 1 upgrades (Armored, Swift), max 1 upgrade
    - Waves 7-10: Tier 1-2 upgrades (adds Unstoppable, Regenerating), max 2 upgrades
    - Waves 11+: All tiers, max 3 upgrades
  - Upgrade effects are absolute per tier (defined in `public/configs/game.json`): a higher tier replaces the previous tier's value instead of adding to it. Gold rewards still multiply per pick
  - Upgraded enemies show a physical effect per pick (1 pick = 1, 3 picks = 3): shield plates in front (Armored), purple glow shell (Unstoppable), ground ring that grows per tier with rising green energy (Regenerating), white speed straps trailing behind (Swift), pulsing phantom shell (Missing Out)
  - Unstoppable enemies resist slows: 25% / 65% / 100% slow resistance per tier, fully negating Slow Tower effects at tier 3
  - Regenerating enemies heal over time (can be countered with burst damage)
  - Missing Out enemies roll their dodge chance on every tower hit (5% / 10% / 15% per tier): a dodged hit deals no damage (the slow still applies, since a slow is a status, not damage) and floats a "MISS" over the enemy
- **Enemy Facing**: every enemy spawns facing along the path (the direction of travel at its spawn point) and its facing refreshes each frame with a smooth turn, so all enemy types — including splitter children — always face down the path, around corners, and from any spawn point
- **Boss waves**: every `4`th wave (4, 8, 12, ...) a **boss** joins the wave *alongside* the regular units — the regular wave is unchanged (same enemies, same counts). The boss is a normal enemy spawned with the rest of the wave, so it **inherits the player's full current upgrade stack** (Armored, Swift, Regenerating, Reinforcements, Missing Out, …) exactly like any other enemy of that wave. Each level defines its own boss in the level config (`boss`: name, `everyNthWave`, base stats, and `hpGrowthPerAppearance`) — Sector 1's is the **Colossus** (1000 HP, slow, large, 5 health on leak, high reward), and each later appearance is stronger (×1.5 HP per appearance) so it stays big without a new mechanic. Sectors 2 and 3 carry placeholder bosses to be tuned later.
   - **Boss bar**: a **big boss bar** (name + wide health bar) appears at the top of the screen while the boss is on the field and hides the moment it dies
   - **Boss-wave banner**: when a boss wave *starts*, a centered **"BOSS WAVE"** flash plays once (fade-in → hold → fade-out) and then fades away, so the player knows the field is about to be dominated
   - **Boss in the next-wave preview**: the in-game next-wave preview shows the boss as a **distinct red row** (skull icon, boss name, and its upgrade-scaled HP for that appearance) above the per-portal enemy list, whenever the upcoming wave is a boss wave — so you see the threat before you commit to the wave

## Levels

Level data lives in `public/configs/levels/` as JSON files and is validated by the `levelConfigSchema` (zod). `PLAYABLE_LEVEL_IDS` (`src/constants/playableLevels.ts`) drives the level picker — only those ids are listed in the menu; `level_main` is the menu background scene, `level_testing` is the non-playable 3D asset showcase (the `/testing-level` route, described in the Features list above), and `stress` is wired only through the dedicated stress-test entry. A unit test (`src/core/configs/levelFiles.test.ts`) validates every playable level file against the schema and geometry (no building/water on the path, cells in bounds), and `level_testing.json` is separately checked for schema validity and a full asset roster.

- **Sector 1** (`level_1.json`) — the opening sector: a single containment line. One serpentine front of 7 waves across a 20×20 grid.
- **Sector 2: The Convergence** (`level_2.json`) — the breach fractures into **two gates** (top-left and top-right). Each snakes down and **converges into a shared final corridor** leading to a single core at the bottom-center. This is a deliberate progression from Sector 1's single front:
  - **Two simultaneous fronts** force you to split your economy and towers across both gates instead of walling off one corridor.
  - **Enemies are split across the two gates** — each wave's enemy groups are assigned to a portal (top-left or top-right), and the next-wave preview above each gate shows exactly who will come out of it (see [Per-portal enemy assignment](#features)).
  - The **shared final approach** is a chokepoint where both fronts merge — AOE, laser and chain lightning shine here, while the core becomes a "kitchen-sink" target.
  - **Ruins** (buildings) in the mid-field and **contamination pools** (water) in the bottom corners are unbuildable, splitting the map so the core can't be cheaply walled off.
  - 8 waves, 20×20 grid, $200 starting funds (a bit more than Sector 1 to cover two fronts).
  - Hand-authored in `public/configs/levels/` (JSON) and checked by `src/core/configs/levelFiles.test.ts` in CI.
- **Sector 3: The Coil** (`level_3.json`) — the vein is a spiral, not a corridor: a **single channel** enters at top-left and winds inward in concentric loops — outer ring, mid ring, inner ring — ending at a core in the **map's center** (grid (10,11)). It changes the shape of the problem instead of adding fronts:
  - **Concentric coverage**: the loops are 2 tiles apart, so a tower placed between two rings reaches **multiple path segments at once** — one tower can cover the outer, mid and inner rings together, which no corridor level allows.
  - The **124-tile single gauntlet** is the longest path of any sector (Sector 1: 26, Sector 2: 33/34): enemies spend a long time in range, and the nested loops leave far fewer dead zones than the far corners of multi-front maps.
  - Two small **pockets around the core** (the rings at grid (8,8) and (10,11)) are the "kitchen sink" — the last stop before the core where everything converges.
  - Rocks are cooled mineral crust and the corner pools are molten vents — unbuildable, they pin the outer loop so the entry can't be walled off.
  - 9 waves, 20×20 grid, $250 starting funds.
  - Hand-authored in `public/configs/levels/` (JSON) and checked by `src/core/configs/levelFiles.test.ts` in CI.

### Adding a level

Levels are hand-authored JSON files in `public/configs/levels/` (`LevelConfigData` from `src/core/configs/levelConfig.ts`): `pathWaypoints` in world coordinates (grid cell `(gX, gZ)` maps to `(-gridSize/2 + gX + tileSize/2, 0, -gridSize/2 + gZ + tileSize/2)` with the game's `tileSize`), `buildings`/`waters` in `gridX`/`gridZ` (their world `x`/`z` are recomputed from the grid at load), `waveConfigs` with `totalEnemies` as the per-wave spawn cap. Register the id in `src/constants/playableLevels.ts` (and the `LevelConfigFiles` union in `src/core/configs/levelConfig.ts`).

Each level also carries **display metadata** and its own **base health**:

- `label` — a short human-facing name shown as the card title in the level picker (falls back to `name`, then the level id). Defaults to `""`.
- `description` — a one-line blurb shown under the label in the level picker. Defaults to `""`.
- `startingHealth` — the player base's max health for that level (each level can have its own). Defaults to `20`. Previously a single `startingHealth` lived in `game.json`; it is now per-level, so the base spawned at run start uses the selected level's value.
- `boss` — an optional per-level boss definition (see [Boss waves](#game-mechanics)): `name`, `everyNthWave` (default `4`), `baseStats` (`health`, `speed`, `size`, `healthLoss`, `reward`), and `hpGrowthPerAppearance` (per-later-appearance HP multiplier). Absent = the level has no boss waves.

All three are editable in the Level Creator (`/editor`, Level panel). The level picker shows `label` as the title and `description` (with the wave count) as the subtitle; the menu scene (`level_main`), the 3D showcase (`level_testing`) and the stress entry still validate against the same schema but do not spawn a base from these values.

Every playable level is checked in CI by `src/core/configs/levelFiles.test.ts`, which enforces: schema validity, at least one path (≥2 waypoints) and one wave (≥1 enemy per wave), buildings/waters never on the path, everything within grid bounds, path segments axis-aligned (the editor's path tool is orthogonal), and no duplicate or overlapping building/water tiles. Run `npm run test:unit` before committing. (The stress level is generated separately by `scripts/generate-stress-level.py`.)

## UI & HUD Architecture

- **UI primitives**: Reusable components under `src/components/ui` (`UIButton`, `UICard`, `UISlider`, `UITypography`, `UIMoney`, `UIModal`, `UIConfirmModal`) provide a consistent design system (variants, sizes, spacing) and are used across all HUD screens for buttons, cards, text, sliders, money display, and modals. `UIModal` is the shared centered dialog (Radix `Dialog` + `UICard`) that `UIConfirmModal` builds on.
- **HUD layout**: HUD screens use structured wrappers in `src/components/hud`:
  - `HUDWrapper` as the root HUD overlay container on top of the 3D canvas.
  - `HUDOverlay` for centered modal-style overlays (game menu, game over).
  - `HUDSidePanel` for right-side panels (main menu, almanac) with responsive widths and scrollable content.
- **Best practices**: Prefer these primitives and layout components when adding new HUD elements to keep visuals consistent, responsive, and easy to extend.
